# Kryteria akceptacji — browser-inspector 2

Każdy punkt jest weryfikowalny (test, bench albo komenda). Numeracja jest stała — testy i CHANGELOG odwołują się do AC-n.

- **AC-1.** Drop-in: `node packages/browser-inspector/bin/browser-inspector.mjs D:/github/app-factory/read.config.browser-inspector.json --stamp X` (bez zmiany configu i argumentów) tworzy `<outputDir>/X/<name>/report.json` dla 6 snapshotów z polami completed:boolean, steps[{description, ok, error}] (error w formie `Error: uczen widzi przycisk nauczyciela`), navigationError tylko gdy nawigacja padła; `pnpm smoke:browser` w app-factory przechodzi po PR z `findRunner` (findScribeDir i jej spec nietknięte), zarówno z `CI=true` (bez keepera) jak i lokalnie z keeperem, uruchomione dwa razy z rzędu.
- **AC-2.** test/compat/smoke-gate.test.mjs spawnuje browser-inspector z fixture'em configu app-factory w trzech trybach (--no-daemon; keeper dwa razy z rzędu — drugi przebieg ma `dziennik-uczen.completed === true` i `nowiro-jezyk.extracts['naglowek-pl']` po polsku; --parallel 3 z identycznym zbiorem `completed`), ocenia report.json kopią evaluateReports(); report.json z keeperem i z --no-daemon są identyczne modulo timing/engine.
- **AC-3.** Czas warm (bench `browser-inspector-warm`: mediana z n ≥ 10 kolejnych wywołań z przerwą 300 ms po `browser-inspector-first`, prawdziwy proces klienta od spawn do exit, flow 18 kroków z bench/task.mjs, checkFindings zielone, `timing.mode === 'warm'` w każdym przebiegu): ≤ 580 ms, tj. ≥ 5,0× wobec mediany warm MCP naive 0.0.80 na domyślnych ustawieniach; projektowy budżet 546 ms (margines 34 ms); p90 raportowany; `browser-inspector-warm-tight` (bez przerwy) i `browser-inspector-warm-fresh` raportowane osobno jako niższe ilorazy; `npm run bench -- --assert-speedup 5` kończy się kodem 0.
- **AC-4.** RAPORT.md ma w tabeli nagłówkowej trzy kolumny MCP (naive, lean, lean --timeout-settle 100) zmierzone tego samego dnia na 0.0.80 i pisze wniosek jako „5× vs domyślne, ~1,8× vs zestrojony settle 100”; żadna liczba w README/RAPORT nie jest wpisana ręcznie.
- **AC-5.** Czas cold: `browser-inspector-first` (keeper startuje w stoperze, steady-state, mediana z 3) ≤ 1,6 s i `browser-inspector-cold --no-daemon` ≤ 1,75 s (budżet 1 469 / 1 618 ms); obie raportowane osobno z jawnym stwierdzeniem, że 5× dotyczy ścieżki ciepłej; „first-ever” po restarcie zapisany osobno i nie użyty w ilorazach; `browser-inspector-cold` czeka na zniknięcie pid i potomnych chrome.exe.
- **AC-6.** Tokeny (o200k, bench): blok AGENTS.md ≡ INSTRUCTION ≤ 200 (limit podniesiony ze 150 — pełna nazwa `browser-inspector` zamiast skrótu kosztuje tokeny, właściciel je płaci; zmierzone 158); batch razem (blok + komenda + stdout + cały report.md) ≤ 420 (400 z wydania 0.1.0 + różnica bloku i komendy z pełną nazwą; zmierzone przy bloku 146: 400); sesja interaktywna naive bez gołego `browser-inspector snap` ≤ 600, z jednym `browser-inspector snap` ≤ 1 000; MCP naive/lean mierzone tym samym harnessem w tym samym przebiegu; wariant `pnpm browser-inspector` policzony osobno.
- **AC-7.** report.md dla przebiegu z sukcesem (6 wartości, 2 błędy — dane z §5.1) ≤ 200 tokenów o200k (test jednostkowy; próbka = 187) i zawiera nagłówek, ## errors, ## values, stopkę more:; ## steps wyłącznie przy porażce; ## verify wyłącznie przy soft FAIL; type page zawsze pisze page.png, flow pisze final.png zawsze przy porażce, a przy sukcesie pomija tylko gdy ostatni wykonany krok był zrzutem.
- **AC-8.** Każda komenda sesyjna drukuje dokładnie jedną linię ≤ 160 znaków i ≤ 40 tokenów (poza find/snap/console/net/eval, które drukują treść z limitem --max 25 i markerem nadmiaru); exit 1 przy FAIL (0 z --soft), 0 przy ok, 2 przy błędzie fatalnym; komenda sesyjna bez keepera kończy się exit 2 z linią `FAIL keeper unavailable…` i nigdy nie uruchamia przeglądarki w procesie; `browser-inspector script plik` wykonuje listę komend w jednym procesie z --no-daemon.
- **AC-9.** Refy: w sesji wykonywany jest wyłącznie pełny page.ariaSnapshot({mode:'ai'}); test regresji — po `verify list` i `find` ref sprzed nadal się rozwiązuje; klik przez `aria-ref=eN` działa na fixture i po nawigacji przez `f<seq>eN`; ref z iframe rozwiązuje się bez `browser-inspector frame`; zmiana etykiety przycisku → stary ref daje `FAIL … ref not found (gone, label changed or other frame) → browser-inspector snap` w < 100 ms, nie po timeoucie; linia akcji niesie navigated/dom Δ/el a→b/+N console.error.
- **AC-10.** Snapshot: kompakt bookstore (952 linii YAML) ≤ 90 linii; `browser-inspector snap` domyślnie 25 linii ≤ 450 tok., 40 linii ≤ 700; kontekst nazw przodka tylko z --names; box-join dopasowuje 100 % linii interaktywnych na fixture; snap.json niesie {ref, role, name, selector?}; `browser-inspector find` zwraca ≤ 10 linii; pola password/one-time-code nigdy nie mają wartości w snap.md/snap.json.
- **AC-11.** Izolacja na jednej karcie: smoke — snapshot A ustawia localStorage, sessionStorage i cookie na DWÓCH originach fixture oraz route i politykę dialogów; snapshot B w tym samym batchu (i następny batch przez keepera) nic z tego nie widzi, `history.length === 1`; scrub między snapshotami trwa ≤ 50 ms na fixture (mierzone jako timing.scrubMs); report.json.timing.ctx = 'reused' | 'fresh' i tab = 'kept' | 'new' zgodnie z faktem; `--fresh` i `isolation:'fresh'` tworzą nowy kontekst z Network.clearBrowserCache i serviceWorkers 'allow'; timing.cacheHits/cacheHitsDocument raportowane.
- **AC-12.** Keeper: auto-start przy pierwszym `browser-inspector` (także batch), nasłuch przed importem silnika, lockfile O_EXCL — drugi keeper wychodzi kodem 0, klient nigdy nie unlinkuje gniazda; drugi klient trafia w ten sam proces; zły token odrzucony; idle-exit po BROWSER_INSPECTOR_IDLE_MS (domyślnie 30 min) liczony od końca ostatniego zadania i tylko przy pustych kolejkach; otwarta sesja podtrzymuje do BROWSER_INSPECTOR_SESSION_TTL_MS; brak keepera po 3 s → batch w procesie z `keeper: fallback` i timing.mode='fallback'; isCI (CI, GITHUB_ACTIONS, GITLAB_CI, TF_BUILD, JENKINS_URL, TEAMCITY_VERSION, BUILDKITE, CIRCLECI) i BROWSER_INSPECTOR_DAEMON=0 nigdy nie zostawiają procesu, BROWSER_INSPECTOR_DAEMON=1 odwraca; hash tożsamości zmienia się po edycji src/ i dla drugiego checkoutu (realpath); `browser-inspector status` drukuje hash, ścieżkę, RSS; `browser-inspector doctor` drukuje `keeper survives shell: yes|no`; page crash odbudowuje kartę, BROWSER_INSPECTOR_MAX_JOBS wywołuje recykling między zadaniami.
- **AC-13.** Start klienta: test/client-imports.test.mjs dowodzi, że `browser-inspector help` nie ładuje playwright-core, engine.mjs ani steps.run.mjs; perf-test (BROWSER_INSPECTOR_PERF=1) — mediana z 5 × `browser-inspector help` ≤ 120 ms; test równości kluczy STEPS ↔ RUNNERS.
- **AC-14.** Sekrety: protokół keepera nie zawiera `env` (test na żądaniu); test przechodzi przez fill/form/storage set/eval z --env, @{NAZWA} i valueFromEnv i asercją sprawdza, że wartość nie występuje w stdout, journal.jsonl, report.md/json, snap.md/snap.json, text.txt, console.jsonl, net.jsonl, logu keepera ani w pliku eksportu (tam valueFromEnv); `@{FOO}` bez zmiennej → exit 2, `@literal` bez klamry zostaje literałem; literał `value` w auth.login = błąd walidacji; `browser-inspector run --file` odrzucone bez BROWSER_INSPECTOR_UNSAFE=1 i w batchu.
- **AC-15.** Parytet: każde z 70 narzędzi @playwright/mcp 0.0.80 ma wiersz w macierzy §7 ze statusem ✅/⚠️/❌ i test smoke lub jednostkowy dla każdego ✅ (w tym `net <n> --body/--req`, `console --level`, `verify list`, `verify --soft`, `dialog` z beforeunload auto-accept i `--once`, `tabs[]` popupów w raporcie, shot png/jpeg/element/full/--mark, storage 3×5, state save/load, trace, video, mouse xy, frame jako zakres CSS).
- **AC-16.** `waitUntil: 'settled'` działa i jest szybszy od networkidle na fixture slow.html o ≥ 150 ms; networkidle honorowane 1:1; `browser-inspector lint-config` na configu app-factory wypisuje 4 sugestie networkidle→settled, 7 sugestii wait ms→waitFor/wait --text (nigdy settled) i parallel: 3; BUDGET.md ma wiersz app-factory parallel 1 i 3.
- **AC-17.** `--parallel 3` na configu app-factory (6 flow) używa trwałych lane'ów scratch[1..2] (nie świeżych kontekstów po pierwszym użyciu) i daje czas ≤ 60 % czasu sekwencyjnego przy identycznych report.json (test na fixture'ach z 3 flow po 300 ms snu każdy).
- **AC-18.** `npm run verify` = prettier --check (120 kol., LF) + vitest (unit, keeper, compat, client-imports) + tsc --checkJs --noEmit + index-code --check + gen-steps-doc --check + check-instruction-sync + smoke — zielone na czystym klonie z `npm ci` przy `.npmrc` ignore-scripts=true, engine-strict=true, Node ≥ 22; playwright-core przypięty exact 1.62.1.
- **AC-19.** `npm run bench` generuje RAPORT.md, WYNIKI.md, BUDGET.md i blok BENCH:START/END w README wyłącznie z pomiaru; BUDGET.md porównuje fazy z tabelą §6, pokazuje queuedMs/scrubMs/cacheHits osobno i czerwieni rozjazd > 25 % oraz iloraz < 5,0; wariant keeper-survives-shell dla cmd/bash/pwsh; pin @playwright/mcp 0.0.80 w bench/package.json, .mcp.json i .vscode/mcp.json pilnowany testem; sondy rewizyjne leżą w bench/probes/.
- **AC-20.** `npm run portable` daje zip z markerem PORTABLE, z którego `node packages/browser-inspector/bin/browser-inspector.mjs help` i smoke na fixture działają bez npm install (test w WP8); docs/STEPS.md i CODE-INDEX.md są generowane i sprawdzane w verify; README dokumentuje `pnpm browser-inspector`, `browser-inspector up` jako hook SessionStart, ACL %TEMP% zamiast 0600 na Windows i listę rzeczy browser-wide (HSTS, HTTP-auth, DNS), których nie czyści ani scrub, ani --fresh.
